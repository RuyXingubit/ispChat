# ISP Chat MVP Architecture Alignment, Security Remediation & Java 25 Upgrade

* **Author:** Ruy / Antigravity
* **Date:** 2026-11-02

## Overview

ISP Chat is a decentralized, peer-to-peer communication network hosted by Internet Service Providers (ISPs). Users hold client-derived deterministic identities (`UUIDv7` + cryptographic keypairs derived from 12-word BIP39 seed phrases) and communicate via End-to-End Encrypted (E2E) text and WebRTC voice/video calls without central servers.

This specification records the architectural alignment, security remediations, and stack upgrades (Java 25 LTS, Spring Boot 3.5, Protobuf 4.x, PowerDNS 4.9, PostgreSQL 17, Coturn STUN/TURN, and X.509 mTLS `extendedKeyUsage`) for the MVP.

## Problem Statement

Prior to this alignment, the repository exhibited six architectural and security gaps between the specification and the codebase:
1. **Virtual Thread Pinning & Port 8080 Exposure (`node/`):** The backend targeted Java 21 (susceptible to Virtual Thread pinning inside Netty/gRPC `synchronized` blocks) and included `spring-boot-starter-web`, exposing an unused Tomcat HTTP server on port 8080 alongside the port 443 gRPC server.
2. **Unbound Identity UUIDs & DHT Spoofing:** User identities lacked a deterministic binding between the 32-byte `Ed25519` public key and `user_uuid`, preventing DHT nodes and peers from statelessly verifying identity ownership or recovering accounts from 12 BIP39 words alone.
3. **TLS 1.3 Certificate Rejections (`ca/`):** Node certificates generated by `ca/generate_node_cert.sh` used 2048-bit RSA keys without `extendedKeyUsage = serverAuth, clientAuth`, causing strict Java 25 and Flutter BoringSSL TLS 1.3 validators to reject mTLS handshakes.
4. **Split Protobuf Drift & Unconfigured xDS (`node/src/main/proto/`):** Protobuf contracts were split across `dht.proto` and `messaging.proto` with mismatched package declarations, while `build.gradle.kts` pulled `io.grpc:grpc-xds` without any Envoy/xDS control plane.
5. **Permissive DNS Zone Transfers (`dns/`):** `dns/master/pdns.conf` allowed `0.0.0.0/0` AXFR/notify and wildcard webserver ACLs, and `dns/master/docker-compose.yml` lacked the `db.local` network alias expected by PowerDNS.

## Goals vs. Non-Goals

* **Goals:**
  * Align `docs/PRD_MVP.md`, `docs/Tech_Spec_MVP.md`, `docs/QA_Strategy_MVP.md`, and `README.md` under a single cryptographic and transport specification.
  * Upgrade `node/` to a headless Java 25 LTS gRPC runtime backed by Redis (`redis:7-alpine`) and Coturn STUN/TURN (`coturn/coturn`).
  * Enforce deterministic `Ed25519 -> UUIDv7` identity binding, canonical `Ed25519` request signatures, and conditional port 443 mTLS federation.
  * Harden `ca/` certificate generation, `dns/` PowerDNS Master ACLs, and Coturn TURN SSRF filters.
* **Non-Goals:**
  * Phase 2/3/4 features (Apache Kafka group chat, BGP Anycast, CDN Domain Fronting, Bluetooth LE Mesh).

## Proposed Architecture

### 1. Java 25 LTS, Headless gRPC Node Runtime & Redis State (`node/`)
* **Toolchain Upgrade:** Upgraded backend from Java 21 to **Java 25 LTS** (with Gradle 9.0.0 and Spring Boot 3.5.0) to eliminate Virtual Thread pinning inside `synchronized` blocks (JEP 491) and reduce heap footprint via Compact Object Headers (JEP 519).
* **Attack Surface Reduction:** Replaced `spring-boot-starter-web` with headless `spring-boot-starter` (`spring.main.web-application-type=none`), leaving only the port 443 gRPC server exposed.
* **Dependencies:** Added `com.github.f4b6a3:uuid-creator:6.0.0` for RFC 9562 UUIDv7 generation, and upgraded gRPC to `1.71.0` and Protobuf to `4.30.2`.
* **Redis & Ephemeral State (`DhtStoreService` & `OfflineMessageQueueService`):** `DhtStoreService` maintains verified Kademlia DHT session records (`userSessions`, 24-hour TTL), while `redis:7-alpine` backs per-recipient offline encrypted message queues (`ispchat:offline:queue:<receiver_uuid>`, 7-day TTL, capped at `MAX_QUEUE_SIZE_PER_USER = 1000` messages per recipient), drained automatically upon a verified `AUTH_HANDSHAKE`.

### 2. Deterministic Identity Binding (`BIP39 -> Ed25519 + X25519 -> UUIDv7`) vs. Temporal Event IDs
* **Seed to Keys (`BIP39`):** The 12-word BIP39 mnemonic produces a 64-byte PBKDF2-HMAC-SHA512 seed:
  * `seed[0..31]` seeds the user's **Ed25519 signing keypair** (`public_key` = 32 raw bytes).
  * `seed[32..63]` seeds the user's **X25519 E2E encryption keypair** (`x25519_public_key` = 32 raw bytes).
* **Deterministic Identity `UUIDv7` (`user_uuid`):**
  * Compute `hash = SHA-256(ed25519_public_key_32_bytes)` and take `bytes = hash[0..15]`.
  * Set RFC 9562 Version 7 bits (`bytes[6] = (bytes[6] & 0x0F) | 0x70`) and IETF Variant 2 bits (`bytes[8] = (bytes[8] & 0x3F) | 0x80`).
  * Preserves 122 bits of SHA-256 entropy, enables stateless 12-word account recovery, and allows every DHT node and client to verify `deriveIdentityUuidV7(public_key) == user_uuid`.
* **Out-of-Band `X25519` Key Pinning via Contact Magic Link:** Contacts exchange verified bundles (`ispchat://contact?uuid=<user_uuid>&ed25519=<base64url>&x25519=<base64url>[&ipv6=<addr>]`) via QR Code or deep link. The client verifies `deriveIdentityUuidV7(ed25519) == uuid` and pins both `ed25519` and `x25519` public keys in its local vault (`SecureLocalVault`) before initiating E2E sessions (`X25519 + HKDF-SHA256 + ChaCha20-Poly1305`), preventing DHT Man-in-the-Middle `x25519_public_key` substitution.
* **Temporal Event & Message IDs (`message_id`):** Standard time-ordered RFC 9562 `UUIDv7` via `UuidCreator.getTimeOrderedEpoch()` in Java and `Uuid().v7()` in Dart.

### 3. Unified Port 443 Security Boundary (`ClientAuth.OPTIONAL` + Strict `ServerInterceptor`) & CA Hardening
* **X.509 Certificate Compliance (`ca/`):** Upgraded node keys in `ca/generate_node_cert.sh` to RSA 4096-bit and added `extendedKeyUsage = serverAuth, clientAuth`. Certificate generation must distinguish hostname SANs (`DNS.1`) from IP literal SANs (`IP.1`) to satisfy RFC 5280 and strict Java 25 / BoringSSL TLS 1.3 validators.
* **Port 443 Split Enforcement:**
  * `NodeRoutingService` and `DhtPeerService` require a verified ISP Chat CA client certificate in `Grpc.TRANSPORT_ATTR_SSL_SESSION` enforced by `MtlsFederationInterceptor`.
  * `ClientStreamService` and `DhtClientService` authenticate end-user Flutter apps via canonical UTF-8 `Ed25519` signatures:
    * **DHT Registration (`ISPCHAT-DHT-V1`):** `"ISPCHAT-DHT-V1|" + user_uuid + "|" + node_address + "|" + timestamp_millis` (with `|now - timestamp_millis| <= 300000` ms clock-skew enforcement).
    * **Message & Signaling Envelope (`ISPCHAT-MSG-V1`):** `UTF8("ISPCHAT-MSG-V1|" + message_id + "|" + sender_uuid + "|" + receiver_uuid + "|" + type_number + "|" + timestamp_millis + "|") || encrypted_payload`, where `ClientStreamService.Connect` requires an initial signed `AUTH_HANDSHAKE` frame where `sender_uuid == receiver_uuid`.

### 4. Unified Protobuf Contract (`ispchat.proto`), Direct `GrpcChannelPool`, DNS & Coturn Hardening
* **Unified Contract:** Consolidated `node/src/main/proto/` into a single `ispchat.proto` (removing `dht.proto` and `messaging.proto`).
* **Direct Channel Pool:** Replaced `io.grpc.xds` with a direct, SSRF-protected mTLS `ManagedChannel` pool (`GrpcChannelPool`) that blocks loopback, link-local, multicast, and RFC 1918 private IP ranges in production mode.
* **DNS Master Hardening:** Hardened `dns/master/pdns.conf` (removed `0.0.0.0/0` AXFR/notify, restricted webserver ACLs), added `db.local` alias to `dns/master/docker-compose.yml`, and upgraded Docker images to `postgres:17-alpine` and `powerdns/pdns-auth-49:latest`.
* **Coturn STUN/TURN SSRF Hardening:** Added `coturn/coturn` (`node/turnserver.conf` and `node/docker-compose.yml`) on ports `3478`/`5349` with `use-auth-secret`, `no-loopback-peers`, `no-multicast-peers`, and `denied-peer-ip` rules blocking private network ranges.

## Alternatives Considered

* **Java 21 Baseline vs. Java 25 LTS:** Rejected Java 21 because synchronized blocks in legacy libraries pin carrier threads under high concurrency; selected Java 25 LTS for JEP 491 (virtual thread synchronization without pinning) and JEP 519 (compact object headers).
* **Standard Timestamp-Based `UUIDv7` or `UUIDv8` for User Identities (Rejected):** Standard timestamp-based `UUIDv7` cannot be deterministically recovered from 12 BIP39 words alone and prevents stateless deterministic `PublicKey -> UUID` verification in the DHT. While RFC 9562 defines `UUIDv8` (`0x80`) for custom hash-based UUIDs, stamping version `7` (`0x70`) bits onto `SHA-256(ed25519_public_key)[0..15]` was chosen to satisfy the strict project-wide `UUIDv7` schema invariant across all UUID fields (accepting the trade-off that identity UUIDs have hash-distributed top 48 bits rather than monotonic timestamps).
* **Separate Ports for Client-to-Node and Node-to-Node (Rejected):** Exposing a separate federation port (e.g., 8443) increases firewall friction for ISP partners and weakens port-443 HTTPS traffic camouflage; single port 443 with `ClientAuth.OPTIONAL` + `MtlsFederationInterceptor` isolates federation RPCs without extra ports.
* **Local `io.grpc.xds` Control Plane (Rejected):** Rejected because deploying and maintaining an Envoy/xDS control plane at every independent ISP node adds operational complexity, memory overhead, and unnecessary attack surface compared to direct mTLS `ManagedChannel` pooling (`GrpcChannelPool`) fed by Kademlia DHT peer discovery.
* **Split `dht.proto` and `messaging.proto` Contracts (Rejected):** Rejected because split proto files caused duplicate message definitions and package drift between edge and federation services; consolidating into `ispchat.proto` guarantees a single source of truth across Java and Dart.

## Risks & Mitigations

* **Static BIP39 Identity Key Compromise:** Because `user_uuid` is deterministically bound to `SHA-256(ed25519_public_key)` and both `Ed25519` (`seed[0..31]`) and `X25519` (`seed[32..63]`) keys are static slices of the 12-word BIP39 seed, rotating a compromised keypair requires generating a new 12-word identity and distributing a new Contact Magic Link. *Mitigation:* Seed phrases and private keys are stored exclusively in hardware-backed OS keystores (`FlutterSecureStorage` / `SecureLocalVault`) and never transmitted over the network.
* **Port 443 Pre-Auth Stream & Interceptor Misconfiguration Risk:** Using `ClientAuth.OPTIONAL` on port 443 means any newly added federation gRPC service that omits `MtlsFederationInterceptor` check would be reachable without a client certificate, and unauthenticated clients could open idle `ClientStreamService.Connect` streams. *Mitigation:* `MtlsFederationInterceptor` is registered globally on the gRPC server, `ClientStreamService` rejects any frame prior to a valid signed `AUTH_HANDSHAKE` within a ±5-minute timestamp window, and `OfflineMessageQueueService` caps queued messages at 1,000 per recipient (7-day TTL).
* **Unbounded `GrpcChannelPool` Growth Under Peer Churn:** Malicious or churning DHT peer addresses could exhaust file descriptors or probe internal ISP networks. *Mitigation:* `GrpcChannelPool` validates every target host against SSRF blocklists (rejecting loopback, link-local, and RFC 1918 private IPs when `devMode=false`) and reuses pooled `ManagedChannel` instances per normalized `host:port`.
* **X.509 SAN Mismatch & PowerDNS Read-Only Config Overrides:** Placing an IP literal inside `DNS.1` in `ca/generate_node_cert.sh` fails strict RFC 5280 hostname validation, and mounting `dns/master/pdns.conf` read-only with placeholder secrets prevents container entrypoint templating unless environment overrides or pre-rendered configs are used. *Mitigation:* Production node certificates must populate `DNS.1` for FQDNs and `IP.1` for IP literals, keeps `ca/*.key` and `.env` excluded via `.gitignore`, and injects real credentials in `dns/master/` before container startup.
